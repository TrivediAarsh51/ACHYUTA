# ACHYUTA Core Domain Model

## 1. Purpose

The ACHYUTA Core Domain Model defines the fundamental objects and relationships used by the Request-Centric Zero Trust Architecture.

It provides the conceptual bridge between the architecture and the eventual software implementation.

---

# 2. Core Model

The ACHYUTA security decision lifecycle is:

```text
Identity + Subject
        │
        ▼
      Request
        │
        ├── Action
        ├── Resource
        └── Context
        │
        ▼
     Evidence
        │
        ▼
      Policy
        │
        ▼
 Risk Assessment
        │
        ▼
    Trust State
        │
        ▼
     Decision
        │
        ▼
 Enforcement Action
        │
        ▼
  Telemetry Event
        │
        └──────────────► Continuous Evaluation
```

---

# 3. Domain Entities

## Identity

Represents the security principal associated with a request.

```text
Identity
├── identifier
├── type
└── authentication_context
```

---

## Subject

Represents the execution entity performing the request.

```text
Subject
├── identifier
├── type
├── process_id
├── parent_process
└── integrity_context
```

---

## Request

Represents a specific security-relevant operation.

```text
Request
├── request_id
├── identity
├── subject
├── action
├── resource
├── context
└── evidence
```

---

## Action

Represents the operation being requested.

```text
Action
├── type
└── parameters
```

---

## Resource

Represents the target of the requested operation.

```text
Resource
├── identifier
├── type
└── sensitivity
```

---

## Context

Represents conditions surrounding the request.

```text
Context
├── timestamp
├── network
├── location
├── device_health
├── session
└── environmental_attributes
```

---

## Evidence

Represents verifiable observations supporting or contradicting a request.

```text
Evidence
├── evidence_id
├── category
├── source
├── value
├── strength
├── timestamp
├── verified
└── metadata
```

---

## Policy

Represents the security rule applicable to the request.

```text
Policy
├── policy_id
├── priority
├── conditions
├── effect
└── scope
```

---

## Risk Assessment

Represents the assessed security risk of the request.

```text
RiskAssessment
├── level
├── factors
├── rationale
└── timestamp
```

---

## Trust State

Represents the current security posture resulting from evaluation.

```text
TrustState
├── state
├── subject
├── reason
└── timestamp
```

---

## Decision

Represents the authorization result.

```text
Decision
├── decision_id
├── result
├── rationale
├── applicable_policies
├── supporting_evidence
└── timestamp
```

---

## Enforcement Action

Represents the technical response to a decision.

```text
EnforcementAction
├── action_type
├── target
├── status
└── timestamp
```

---

## Telemetry Event

Represents an observation generated by a security-relevant system component.

```text
TelemetryEvent
├── event_id
├── source
├── event_type
├── timestamp
├── payload
└── integrity_metadata
```

---

# 4. Architectural Separation

ACHYUTA intentionally separates:

```text
Evidence
   ≠
Policy
   ≠
Risk Assessment
   ≠
Trust State
   ≠
Decision
   ≠
Enforcement
```

This separation prevents individual components from becoming responsible for unrelated security functions.

---

# 5. Core Principle

> A security decision must be explainable through the request, evidence, applicable policy, risk assessment, and resulting decision.

This provides decision traceability throughout ACHYUTA.

---

# 6. Example

Consider:

```text
Subject:
powershell.exe

Identity:
Administrator

Action:
Read

Resource:
LSASS Memory

Context:
02:13 AM
```

The request is evaluated using available evidence.

Possible evidence:

```text
- Process signature
- Parent process
- Command line
- Integrity level
- Defender telemetry
- Sysmon telemetry
- LSASS access event
```

The policy engine determines which rules apply.

The risk engine evaluates the request.

The decision engine may produce:

```text
Decision:
Quarantine
```

The enforcement layer then performs the appropriate technical action.

The resulting activity generates telemetry that becomes future evidence.

---

# 7. Continuous Evaluation Loop

ACHYUTA is not intended to make a single permanent authorization decision.

Instead:

```text
Request
   ↓
Evidence
   ↓
Policy
   ↓
Risk
   ↓
Decision
   ↓
Enforcement
   ↓
Telemetry
   ↓
New Evidence
   ↓
Re-evaluation
```

This loop supports continuous verification.
